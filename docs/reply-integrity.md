# 主用户 QQ 回复事实核实

版本：companion-adapter 0.65.1 / qq-bridge 0.15.3。B站和调度插件保持原版本。

## 本次解决什么

真实回合84曾把已经 completed / rested 的旧阅读请求说成“还在队列里”；回合85只执行召回，却说“字幕原话核对通过”。回合86真正执行逐字核对，取得一条通过、两条不匹配，正确更正了旧说法。本次保留这些原件，以三轮原事件做本地只读重放，不修改旧回答或重新发送。

## 执行流程

1. 在 DSH 原有 `agent/turn-stopping` 扩展点，读取本轮真实主用户消息、最后一条模型草稿、成对的工具调用及结果。
2. 遇到明确的引文核对通过措辞，验证本轮 recall 的 token、Source/View/read 身份、正文哈希，以及 evidence_check 对应的逐字原文。召回、旧回合、单条通过均不能替其他引用背书；只核对候选内的逐字出现，不认证语义、现行事实或重新读过视频。
3. 遇到带完整 UUID 或8位缩写的后台阅读请求状态声明，从同一QQ会话现有 activity_requests 账本读取，并复核原请求来源。终止结果不能说成排队；不读取另一会话的任务正文。
4. 不符时，以独立的宿主上下文来源给原模型一次同回合修正机会。这不是主用户新消息。只可按原权限召回/核对、读取活动回执和调整回应意图；不允许借修正重复观看、写记忆、排队或操作平台。
5. 主用户QQ文字桥在入队前及实际发送前再校验。仍不符或来源不一致，保留原草稿和错误记录，停止发送；不改成成功，不自动重发，不抹掉旧失败。

## 数据与职责

- 新代码：`plugins/companion-adapter/src/reply-integrity.js`；宿主接入在 agent.js 与 qq-host.js。QQ桥只提供校验调用点，记忆、人格及任务事实仍归原模块。
- 没有新数据库或表。原草稿、宿主修正及工具调用保留在 DSH 会话。阻止发送原因在 qq_inbox.error 和已有 qq_reply_events（reply_integrity_blocked）；已准备的分段可以标为 blocked，计划为 interrupted。
- 不重置或扩大任何调用额度。普通闲聊及正确回复不增加模型步骤；发现问题时最多增加一次原聊天模型的修正步骤，必要只读检索仍消耗原额度。
- 沉默意图不因核实变成强制回复；情绪、措辞、兴趣与回应时机仍由原机制及模型选择。原 /stop 确认和真实发送结果不明的禁止重发规则保留。

## 边界及代价

首版覆盖主用户 QQ 私聊的普通文字最终回复。群、其他好友、空间、B站及主动联系沿各自现有流程，未宣称已统一接入。状态检查针对**有ID的后台视频阅读请求**，不涵盖所有任务种类或无ID的模糊代称。

措辞识别采用有界规则，不是通用自然语言真实性证明；未覆盖的新说法可能漏检，复杂表达可能误拦。否定、历史陈述、引用旧说法和条件句有专门回归。引用检查也不能证明科学结论为真、语义推断正确或看完视频。

发现问题可能增加一轮模型耗时；修正后仍不符会导致这条QQ回复未发出，原因保留可查。发送前读回只证明当时状态，远端接收前仍可能发生变化；多段发送无法做到平台端原子提交，已发部分不能撤回。不会为测试放宽这些边界。
