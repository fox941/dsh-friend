# 共同经历与用户事实的证据分级（待实现设计）

2026-11-07。本文是方案，不表示新的经历写入器已经部署。

## 当前代码的实际边界

日常 `friend_memory_write` 只接受本轮主用户引文，适合用户事实、偏好、明确约定；不适合把双方多轮互动都作为用户陈述提交。

夜间整理并非只能读用户：`preview-sessions.js` 能提取持久化的 user_message 和实际已发送的 assistant_response。`apply-evidence.js` 会核对来源、内容哈希及发送状态；`apply-plan.js` 仍要求非外部观察应用至少有一条用户依据。因此“AI 的一半永远无法记住”不准确，但缺乏明确的共同经历类型及日常入口确实会造成误拒和主体归属混淆。

## 推荐方案

继续使用 Mnemon + Native 存储、现有 Source/View 权限、独立审核、备份和版本保护。改造提案及证据模型，不因这一个问题迁移整个记忆引擎。

| 类型 | 核验依据 | 允许的表述与限制 |
|---|---|---|
| 用户陈述／偏好 | 用户实际发言、平台与账号身份、原文片段 | 可概括，但引文逐字可查；“用户说自己喜欢……”不等于客观事实已证明 |
| 共同经历 | 同一事件窗口中实际持久化的双方发言、顺序和发送回执 | 可写“我提出A，你选择B，我后来改口”；不要求用户复述AI说过的话 |
| AI主观感受／解释 | 自己的表达及触发经历，独立评价状态 | 写成“我当时觉得／我推测”，不冒充用户立场、不直接固化人格 |
| 工具／外部观察 | 实际成功回执、观察原件及读取范围 | “答应去看”不等于已看，“说已完成”不替代真实工具回执 |
| 日记、梦、小说 | 工作文件、版本及创作时间 | 可检索创作，但不自动成为现实经历或用户资料 |

新增 `shared_episode` 提案应包含：事件ID、参与者及说话人、发生时间、记录时间、会话及消息引用、原文区间、内容哈希、摘要、AI视角、确认状态和可见范围。摘要是索引，原文是核验依据；引用不能由模型自造。

确认状态区分“会话可核验”“用户明确确认”“有争议／已更正”。普通有原件的互动不必每次要求用户确认；对关系、承诺含义或争议解释再询问。没有明确确认，不能自行标为“当事人已确认”。用户确认也不等于证明客观外部事实。

AI可以是事件当事人，但只能为自己的发言、选择和已核验操作提供依据。不得把“我猜用户难过”变成“用户难过”，不得把“我承诺执行”变成“执行完成”。原有私聊／群／公开空间的披露规则继续沿用。

## 落地顺序与验收

先补类型及来源引用，再接专用经历提案入口和夜间整理；验证双向发言、AI改口、未发送草稿、失败操作、转述被误当立场、明确确认、更正与重复整理。必须证明新入口没有放宽用户画像、更正及跨场景披露权限。

检索需保留经历类型及来源，允许回到原文核对。事件ID防止同一互动反复写入；修订保留历史与 superseded／disputed 状态。程序校验和模型审核各负其责，不能声称消除了所有语义误判。

## 现成方案参考

- [Hindsight Retain](https://hindsight.vectorize.io/developer/retain)：明确区分 world 与 experience，以记忆主体是否亲历／参与决定归属，可参考其完整叙事和经历建模。它不会自动替我们实现当前的账号身份、QQ发送回执和审核策略。
- [Mnemon 扩展与存储文档](https://github.com/omdsh-dev/dsh-mnemon/blob/main/docs/en/README.md)：现有 Source、Strategy、Provider 分层允许保留后端并调整提案、审核及检索展示。替换 Provider 不会自动改变 companion-adapter 上层的用户引文限制。

推荐采用 Hindsight 的类型划分，自研一层薄的经历提案／证据适配，复用既有 Mnemon 存储和保护流程。无需为了这个问题并行再维护一套人格或记忆库。
