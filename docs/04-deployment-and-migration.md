# 部署、持久数据与迁移

更新：2026-10-27。开发实例已在 runtime/dev 运行，使用官方 DSH 发布包、DeepSeek 和 Mnemon/Native。以下包含后续目标布局；已实现路径、备份命令及迁移限制见 [运行说明](06-running.md)。家用 prod、人格状态和跨机器启动尚未部署或验收。

## 实例布局

```text
runtime\dev\                   公司电脑的开发实例，不替换家用 prod
runtime\prod\                  家用电脑的长期实例
  dsh-home\                    启动进程的 DSH_HOME
    sessions\                  DSH 管理的会话数据
    storages\                  DSH 管理的其他状态
    profiles\web\              实例的 profile 配置、插件安装记录和锁文件
  companion\
    companion.sqlite           自我、身份、提案、检查点、后端映射
    artifacts\                 真实外部经历凭据
  memory\                      显式配置的 Mnemon storageRoot
    runtime\                   用户画像、工作记忆与投影
    documents\                 显式索引的文档；个人日记适配待开发
    data\<space-id>\           Native mnemon.db 等后端数据
    state\                     连接、机器标识等必要控制状态
  workspace\
    self\                      自我描述和个人提示词的可读导出
    diary\                     日记导出
  exports\                     版本化可交换导出
  manifest.json                以后由备份程序生成的实例清单
```

上图是完整目标布局。目前实际生成的是 dev 的 dsh-home、memory、workspace、logs 和按需 exports；companion、self、diary 与 prod 尚未创建。DSH 内部路径以固定版本真实生成的结构为准，第三方插件路径须逐个验证。

启动时在进程环境明确设置 `DSH_HOME` 为对应 `dsh-home` 的绝对路径，再通过 `dsh` 的受支持 profile 启动；不要把 `DSH_HOME` 仅写进 `.env` 期待它决定主目录。工作区同样明确指定，不能无意使用公司代码目录。

Mnemon storageRoot 单独指定到实例内的 memory 目录；Native CLI 和平台凭据的实际路径也须核验。不能假定 DSH_HOME 自动约束所有第三方插件。

设计上的两组路径互不重叠：开发进程不能指向 prod，部署脚本不能默认复制 dev runtime。会话、角色、联系人和记忆库也不能只靠当前用户名自动匹配。

## 停机迁移流程

1. 暂停自主活动、夜间整理及各渠道入站；等待正在写入的操作结束，记录未完成任务和未知发送结果。
2. 正常停止整个实例及其插件/桥接写进程。确认所有数据库写者退出；不能只关闭浏览器页面。
3. 生成一致性备份：优先用各后端支持的备份/导出；离线目录备份应覆盖完整 `runtime/prod`，并保留 SQLite 的 `-wal`、`-shm` 等实际存在的伴随文件。不要只复制某一个 `.db`。
4. 清单记录实例/角色 ID、DSH 提交和版本、插件版本/包校验、schema 版本、文件数量与哈希、备份时间、操作检查点及所有数据根目录。密钥备份另行加密管理。
5. 新机器先准备同版工具和依赖，把数据恢复到新的 staging 实例目录，不直接覆盖已有活跃 prod。
6. 更新绝对路径，重新验证主用户账号绑定、工作区作用域、凭据、平台登录。迁移工作区路径可能改变基于路径派生的 scope，因此首期使用显式固定身份作用域。
7. 先离线检查 schema、记录数量、来源引用和待办，再在关闭自主发送的情况下启动。验证旧聊天续接、关键记忆检索、当前自我状态和一项未完成约定。
8. 通过验收后切换 prod；旧机器停止运行，避免两个独立副本继续分叉写入。回退必须同时恢复兼容代码和数据，不让旧程序打开新 schema。

因此可以用压缩包迁移，但包里必须是停写后的完整数据快照、清单和兼容版本；不是“随手复制一个 runtime/dev 替换家里目录”。跨机器长期双向同步不在首期范围内。

## 插件更换

同一个后端升级先备份，按其正式迁移工具升级 schema，不能直接改数据库版本号。Mnemon 的策略切换与 Provider 更换是不同操作；更换后端仍需要数据转换。

Mnemon Pack 只备份其正式支持的内容，不等于整个角色。完整迁移还需 DSH 会话、companion.sqlite、外部原件和 Pack 未包含的状态/凭据；必须按固定版本的实际导出清单核对。

换后端时，原始会话和外部经历仍由实例保留；导出状态、变更依据和后端记忆。转换器保留业务 ID、作者、时间、有效期、来源、类型和置信度，建立新旧 ID 映射，再重建检索索引。

目标角色交换包设计为 `ai-friend-export/1`，包含身份、状态事件、提案、记忆和证据等内容。完整字段规范与跨后端导入器尚待实现。当前已实现的导出是 Runtime、Documents（存在时）、Native 原始表和便于检查的 memories.jsonl，并非已完成的角色交换协议。

向量只是派生索引；替换嵌入模型后通常重建。某个后端无法导出的压缩摘要、隐藏状态或未保留原文，可能造成信息损失，迁移前必须列出。更换推理模型或召回器也会影响表现，保留文件不能保证语言和行为逐字不变。

保留可回放的经历与状态、实际做恢复测试，比把某个插件或数据库文件称作“灵魂”更能保护长期连续性。
