# 读取消息与执行账号候选的阶段区分

companion-adapter 0.26.1；attention-scheduler 0.2.0；架构 v0.28.1。

真实平台验收中，收藏请求已通过模型、原统一注意力、B站实际POST与读回确认。随后关注请求在消息入口被模型放弃，理由是“没有关注操作候选”。此时尚未把该消息交给原角色理解，本来就不应已有执行候选。这是模型对两种处理阶段的混淆，不能把该理由解读成情绪不佳或已经执行关注。

此次仅在统一注意力的系统说明中明确：

- message表示是否把原话交给原会话读取与理解，随后才可能产生候选。
- 带biliActionId的browse表示处理已存在的账号操作候选。
- 选择读取消息，不等于授权或提交平台动作，也不保证回复；后续来源、权限、统一调度和执行核验仍生效。
- 模型仍可根据实际状态暂缓、忽略或安静，但不能把当前阶段本就没有执行候选误当成无法读取消息的事实。

没有强制聊天优先、重放被忽略消息或预先批准关注。原被放弃事项保留原记录；后续明确验收使用新的消息，并先确认没有形成过账号写入候选。旧收藏回执与其撤销权保持不变。

没有修改DSH、Mnemon、调度状态机、工具权限、数据结构或模型供应商。数据和迁移方式沿用35号文档，升级前停机快照并核对旧表、记忆、身份与凭据。

验收使用独立DSH、实际DeepSeek及模拟平台HTTP；这一轮启用真实统一注意力，由原调度选择消息和账号候选，测试驱动器不直接执行账号任务。真实账号后续核验记录单独保存，不能把模拟传输称作真实平台写入。
