# 同一事件的双记录对比与漏召回修正（0.59.2）

此前真实QQ要求对比同一段视频的“只读字幕”与“后来抽样画面”两份记录，召回器只交给模型其中一份，完整对照未通过。0.59.2依据本地复现调整任务指引，不增加检索后端、模型角色或存储。

## 定位结果

对当前Native创建一致性SQLite备份，各方案使用相互独立的副本，重放真实两条查询，经实际Memory Spaces Source、Native Provider及原分层Strategy执行；真实原文只在本地处理。

第一轮Source已返回两份原件：画面记录排第1，旧字幕记录排第2，二者都是medium。普通路径每次保留一条medium，字幕原件因此在Strategy筛选时被排除。普通路径输出的两条ID和1889字符与真实QQ记录一致。第二条宽泛英文查询则引入其他视频。该结果表明本例是普通模式的候选筛选与任务规划不匹配，而不是旧原件被删除。

保持原查询不变，只声明现有complexReason后，两份原件都会保留；第二种以已出现视频ID和“未观察画面/声音”等类型词定向查询，也能找回。副本包含16条有效记忆、0条嵌入，未启用向量服务。复现使用事后快照，访问计数可能不同于原回合；本次恰好重现相同候选输出，不把结果泛化为任意资料排名。

## 修改范围

- 同一事件或视频的多次观察、字幕/画面记录、修订版本对照，也属于复杂回忆。模型应在首查填写具体complexReason，说明需要哪几份原件。
- 先检查每一侧是否真实召回；缺一份，在剩余额度内按已有来源ID、标题、时间、观察类型定向补检。只有一份原文，不能用一般常识编出另一份。
- 普通模式误启动后仍可由模型给出复杂理由，并用实质不同查询补检。重复同一查询仍只重放当时已接纳的证据，不偷偷重新读取或补回更多候选。
- 调整Mnemon路由和额度耗尽提示，使其与同事件多记录对比的定义一致。

普通两次查询、每次1条medium、最多8条结果保持原样；复杂最多4次查询、每次4条medium、最多12条结果保持原样。全回合12K正文、每条2K、同一Source权限、引用凭证、低相关排除、去重和写入审核均未改变。是否选择任务和检索词仍由当前模型决定，程序未按关键词自动开大额度。
