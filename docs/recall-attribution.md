# 回忆回答的回合与逐份来源归属

2026-11-03，companion-adapter 0.59.3。

## 触发问题

0.59.2真实QQ对照已找到字幕与画面两份原件并分别核对引用，但最终回答仍出现两个附带问题：把上轮的另一视频材料称作本轮召回；把只在后一次原件明确出现的“不再回原洞穴”概括成两份都记载。原验收中的失败记录保留，不追记为通过。

## 实现

复用RecallEvidenceLedger现有的真实Agent、Session和用户事件位置。当前回合首次建立台账时生成随机turnId，多次召回和引用核对共用；实际用户事件或回合变化就换新标记。它是观察回合，不是原件发生时间，也不是原件内容版本。仍用原来的Source/View/readId及正文哈希核对原件。

friend_memory_recall和friend_memory_evidence_check返回evidenceContext：turnId、scope=current_user_turn、includesPreviousTurns=false。results只表示这次调用返回的材料，不自动并入上轮来源。旧凭证跨轮仍拒绝；空结果也有新回合标记。turnId由宿主生成，模型不能提交一个标记来恢复旧引用。

每条引用核对结果增加supportScope=this_source_only。逐字匹配仅对应该条id的原件，不能扩展成另一份材料也支持此细节，更不认证整段语义。规则要求回答区分当前回合、上轮材料和推断；可以明确沿用上轮信息，无需为改称来源额外查询。说“两份都记载”前，分别检查每份正文；单份细节单独归属，未提及不等于事情没发生。标记供内部使用，通常不展示给用户。

没有增加最终回答审核模型，没有逐句机械改写输出，也没有强制每次对话检索。原普通/复杂查询额度、12K正文额度、身份和Source权限、长期写入审核继续沿用。台账只存当前进程内的观察凭证，不创建新数据库表或复制记忆库。

## 验证

68项源码专项和68项独立安装包专项通过。新增4项分别验证：同轮多次读/核对标记一致；同消息标签的新实际回合换标记且旧凭证失败；单份引用不能验证另一份未记载细节；新回合空结果不继承旧来源。

实际DeepSeek工具循环另使用4组纯虚构资料：上轮钟楼来源不在本轮风筝结果；纸船后续仅第二份有；灯笼后续两份确实都有；上轮有明信片而本轮无候选。逐案检查回答中的回合及共同/单份归属，4组目标条件符合。每次比较都实际调用本地注册的召回和引用核对工具；空结果未伪造引用。真实记忆、聊天和备份未发送到额外模型评估。

这些样本不证明整个回答所有断言都正确。空结果样本出现过度展开技术字段、对历史措辞作多余解释的表达问题；保留原始输出，不据此宣称模型零幻觉。Source/引用的技术约束可以硬验证，正文的语义归属仍依赖模型理解。真实QQ复验和手机可见性单列，部署本身不视作该项通过。

源码：plugins/companion-adapter/src/recall-agent.js、recall-evidence.js。验证：tests/recall-attribution.test.mjs及原回忆专项。发布/模型报告：.work/recall-attribution-*。
