# 夜间增量整理恢复（0.56.0）

本次修复 2026-11-03 只读记忆审计中发现的调度断点，不更换 Mnemon、人物画像、自我状态或情绪存储，也不强制 AI 进行整理。

## 原因

原夜间任务的预演模型因 max-tokens 未返回正文，任务进入 retry_wait；统一注意力却把这次执行当作 completed。同一 run 再次提交仍匹配到这条终态候选，因此一直没有新的可选择工作。旧待办还会遮住过期日程的更新。

## 修复后的流程

1. 到期日程先前移。若已有未完成自动增量，则合并至该 run，避免积累一夜一条的重复写入任务。
2. 同一次整理使用 run ID 和原授权请求摘要标识。重试、额度等待、让路、中断沿用原检查点及回执；主用户明确发起新的 retry 请求，才产生新的候选标识。重复送达同一请求不会重置进度或次数。
3. 资源未就绪时，注意力候选进入 waiting，按真实 not_before 唤醒。唤醒只让模型重新选择，可以继续、暂缓或放弃，绝不直接提交旧草稿。
4. 已有的 legacy 完成候选留作历史，原 run 仍可恢复时创建带请求摘要的新候选；仍有效的旧等待候选原位接续，保留模型选择的唤醒时间。旧放弃/取消候选不会自动复活。
5. 调度宿主关闭会中断正在执行的审核，记录 interrupted 并保留检查点，不额外消耗失败重试次数；重启后重新考虑。对方忽略取消信号也不能晚到提交。

应用仍复用原记忆保护层：有改动才备份、逐字原件校验、版本比较、应用幂等回执和部分失败人工核对。needs_attention 不会被后台自动重放；失败次数耗尽后也不会无限重试。

## 预算与来源兼容

- 预演默认输出由 4096 提至 8192 tokens，包括模型推理所用输出预算；显式自定义配置保持原值。输入范围、批次数、每日额度和重试次数未扩大。更大的单次上限可能增加耗时和费用，也不保证模型永不截断。
- 当前 DSH 工具结果使用 message.toolCallId；读取器兼容旧 message.callId。两字段冲突、错误结果和不在原观察白名单内的工具，不作为新观察。
- 没有添加新模型角色、后台循环、数据库表或依赖；没有回填虚构记忆、清空历史或重复发送平台消息。

仍使用 runtime/dev/companion/companion.sqlite 中的 nightly_*、attention_*、预演与应用表，长期内容仍在既有 memory 数据目录。迁移沿用当前完整 runtime 搬迁流程，不需要新增数据目录。部署前保存一致性快照与被改源码；安装期间核对原身份及角色数据摘要。
