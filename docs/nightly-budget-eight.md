# 夜间整理调用余量与资源等待恢复

2026-11-04，companion-adapter 0.62.6。

主用户已同意长期将夜间整理调用上限由每天4次提高到8次。它是每日后台模型请求上限，不是8个日程，不会在每轮普通聊天后启动夜间整理。北京时间02:00产生日程候选、每次最多两批、统一注意力自主选择、实际有依据才处理等规则不变。预演、结构纠正和应用审核合计计数；其他预演/共享应用/聊天/成长等额度继续各自限制，没有提高单次tokens上限或重置用量。

nightlyConfig默认值改为8；显式配置dailyCallLimit（包括较小值）继续优先。现有主实例nightly只配置enabled、time和timeZone，将沿用新默认值8，runtime和源码迁移一并携带即可。当天已用4次仍为4次，升级后剩余4次；额度按北京时间自然日计账，不退还失败或中断尝试。

两批各执行一次预演与独立应用审核通常已需要4次调用，8次为格式纠正、普通失败重试留出余量；无需变更的批次仍可以不调用应用模型，额度不要求用满。8次是工程余量，长期实际消耗还需多日观察。

## 恢复已有应用审核

旧任务已经产生有效报告，却因旧上限不足而保存“次日再试”的资源时间。仅提高上限不会消除该旧等待，因此新增窄范围恢复检查，复用原30秒宿主检查，不增加定时器：

- 原任务仍为budget_exhausted，错误必须精确对应本层“提案应用审核未完成：今日夜间整理模型额度已用完”；未知失败不推定为额度问题。
- 夜间自身和共享应用审核额度当前均可用；仍有完整有效报告，提案不为空，已有应用尚无固定写入计划。
- 使用统一注意力时，必须是同一授权对应的waiting候选，waitSource=resource、任务编号和持久等待时间完全匹配。模型自己的暂缓、取消、放下、失败和旧授权候选保持原样。
- 保留报告、应用记录、尝试次数、失败重试次数和已用额度；只将资源条件已变化的候选重新交模型选择。任务与候选状态在同一事务提交，失败整体回滚，不强制开始。

恢复后的应用审核会重新核对当前来源、旧资料与后续证据。只有独立审核通过且有实际修改，才进入原一致性快照、写入和读回流程。模型仍可暂缓或放下。已经存在固定写入计划或不确定写入结果的任务，不经此入口自动恢复。
